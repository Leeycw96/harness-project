# Keel Dev 的 ASO 职责分离

## 范围与依据

用户确认 A（Agent）、S（Spec）、O（Orchestration），要求规范 Builder、QA、CallChain 定义并收敛公共资料，保持 full/fast 的既定效果。只重组指令及引用；可选的 aso_bindings 记录本次角色和规范选择，不改计划格式、既有运行脚本 API、阶段、完成标记、产物名称或版本。

## 职责与文件

- A：三个 Agent Markdown 保留“角色、能力、原则”，原则对应原有要求并直接说明如何行动。TOML 只注册并加载自身角色，不包含 Spec 路径或阶段步骤。
- S：`common/refs/keel-dev-spec.md`、`keel-qa-spec.md`、`keel-call-chain-spec.md` 分别承载开发、验收、流程维护的操作约束与规范。项目手册提供具体语言、架构、目录和命令；Spec 不导入 Agent 或编排。
- O：full/fast 和 `common/refs/keel-dev-orchestration.md` 选择角色与 Spec，按次提供目标、范围、资料和任务章节。阶段、提交、进度、重试、完成与恢复仍由编排决定。

公共引用目录保留三份按职责拆分的 Spec 和一份编排文档，不再单独设置 rules、environment、protocol 或 tasks 文件。各 Spec 包含本职责的操作边界。代码与测试标准只在 dev Spec 中维护，QA 通过编排下发的章节引用读取同一份标准；更换开发 Spec 时同步验收引用。Spec 是工作规范，本次功能目标、模型、接口和实现设计仍来自已确认 Plan。

## 引用与读取

编排按 builder/qa/call_chain 在 `state.json.aso_bindings` 中保存 agent、spec_refs、task_ref，fast 仅前两项。A/S 可独立替换；恢复沿用本次绑定，缺少绑定的旧 run 使用默认值。替换不改变目标、用户授权或门禁。

引用为绝对文件路径，可附 `#二级标题`。片段只读取对应二级标题及其子节，到下一二级标题结束；无片段读全文。引用缺失或冲突须阻断，不能猜测默认资料。

| 执行者 | Spec 引用（另加项目手册） | 编排章节 |
| --- | --- | --- |
| 主会话 | 按任务选择规范 | 主会话编排 |
| 实现 | dev Spec | 通用任务要求、实现任务 |
| 验收 | qa Spec、dev Spec 的代码与测试标准 | 通用任务要求、验收任务 |
| 流程维护 | call-chain Spec | 通用任务要求、流程维护任务 |

只下发当前职责的引用。子任务不得读取主会话编排、其他任务章节或流程预判状态，不自行调度或推进阶段。

## 内容迁移对照

| 原内容 | 归属 |
| --- | --- |
| 角色、能力、最小修改、不过度设计、TDD、按计划执行等原则 | A：各角色定义 |
| 操作边界 | S：各职责 Spec 的操作约束 |
| 真实实现、架构、测试范围及质量、验收红线 | S：dev Spec 的代码与测试标准，供实现和验收共用 |
| CallChain 更新条件、当前状态图与流转表标准 | S：call-chain Spec 的业务流程索引 |
| 读取当前快照、按功能加载、进度、完成与基线失败处理 | O：通用任务要求 |
| BUILD/FIX 系列阶段、输入与提交 | O：实现任务 |
| REVIEW 系列阶段、范围与验收报告 | O：验收任务 |
| CALL_CHAIN 的输入、报告及独立文档提交 | O：流程维护任务 |
| Preflight、恢复、修复上限、按需调度、阶段推进 | full/fast 与 O：主会话编排 |

## 原则表述与原有要求对应

原则用能直接指导行动的名称和说明，不用抽象标签替代已有要求。下面对照修改前的 Agent 定义及其引用的代码质量规则；A 表达稳定工作原则，S 保留项目操作边界、具体标准及验收阻断条件，O 保留执行步骤。

| 原有要求 | Builder 原则 |
| --- | --- |
| 已确认契约不得增减或重定义；不重选关键方案 | 按计划实现 |
| 每处修改对应目标；完成必要联动，不顺手重构、改格式或删除无关代码；只清理本次无用代码 | 最小修改 |
| 选择直接、可维护的实现，不为未来需求增加抽象、功能或开关；保留必要错误处理、安全和一致性约束 | 不过度设计 |
| 沿用项目架构、职责划分、风格与测试工具，不强制增加分层 | 沿用项目写法 |
| TDD 验证关键正常、异常分支与副作用；修复先复现，不为机械修改强造测试 | 先写测试，再写实现 |
| 不用 stub、fake 或硬编码成功响应代替交付；测试替身不能替代真实实现验证；依赖缺失报告阻断 | 交付真实实现 |
| 在问题源头修复，不调整断言或参数掩盖失败 | 修复根因 |
| 计划矛盾、关键决策缺失或与代码事实冲突时报告，不自行猜测或改写 | 遇到方案矛盾先报告 |
| 按目标运行相关测试和项目检查，记录证据；验证修复和关联行为，未执行不算通过 | 验证后再报告完成 |

QA 用“实际运行验证、检查完整行为、按既定标准验收、区分新旧问题、问题要有证据”承接原有验收要求。CallChain 用“按现有代码记录、讲清业务流程、标明代码位置、只改受影响文档、图文同步更新”承接原有维护要求。仅改写和补全原则表达，不增加任务或改变门禁。

## 不变条件

角色定义规范化不改变既定目标、任务范围、验收标准或交付要求。能力栏目只描述专业能力，不增加独立调研、方案重选或文档交付阶段；实际工作由本次任务与规范约束决定。TDD 的方法归入 Builder 原则，Spec 中的关键正常、异常分支、副作用覆盖和测试质量要求保留。

full 保持 Preflight → BUILD → REVIEW → 按需 CallChain；fast 保持 BUILD_FAST → REVIEW_FAST，禁用 CallChain。QA 阻断进入原 FIX/复审循环，最多 3 轮。主构建失败停止；测试准备失败仅经用户明确允许继续。审查 5 分钟、构建/修复 15 分钟无进展触发检查，每阶段每角色最多恢复 2 次。

QA 只审本轮 Builder commits，完整验收覆盖所有功能；复审限阻断与受影响场景。基线失败与本轮回归区分。状态机变更从 fast 转 full。CallChain 主会话不能确定时保守调度；独立维护者仍按原门禁判定，不确定不更新并报告缺口。shadow 不暴露预判；on-demand 仅明确无变化时跳过。Agent 不直接通信、调度或等待其他 Agent；只提交职责内内容，不自动合并或推送。

## 验证

检查角色不引用 Spec/编排、Spec 不引用角色/编排；临时部署校验文件和章节引用可达。验证重新部署能清理 manifest 中的旧文件并保留用户自有文件。保留阶段、tag、输入/输出和权限要求，验证 full/fast 初始化、进度与完成、旧 profile、CallChain 跳过/更新/shadow 的兼容。

体量按明确下发的章节统计，同时展示整份文档大小。开发与验收的旧缩减基线不含原先独立的代码规约；完整默认任务体量仍包含全部 A/S/O 资料。运行助手和计划资源保持不变。静态与契约检查不替代真实模型任务评测。
