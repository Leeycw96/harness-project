# 独立 BUG 定位与局部修复

## 已确认边界

keel-fix 接收 BUG 后编排 Builder 根据问题、代码、配置和日志定位，本地复现不是前提。主会话根据证据判断：明确且局部、不改变既定业务约定的缺陷进入 fix；需求变更或修复需要业务状态/流转、业务流程、接口契约、数据模型/迁移、高风险设计变化时，说明原因并提示用户走 keel-plan。无法定位继续取证，不直接判需求。

fix 仅使用 Builder 与 QA，不调用 Plan、Dev 或 fast Skill，不调度 CallChain。缺陷也可能需要 Plan 评审；分类与执行路径分别记录。新增日志的观测能力改造独立说明并提示 Plan，原 BUG 保持待定位。

## ASO

- A：复用 Builder 的定位、修复、证据与实事求是原则，复用 QA 的独立验收。Agent TOML 不调整。
- S：复用 dev Spec 的操作约束、定位标准与代码测试标准，复用 QA Spec；Spec 不管理阶段或用户确认。
- O：keel-fix 负责分流、取证沟通、HTML 审阅、每个 BUG 的用户确认、修复与 QA 返修、暂停与恢复。Agent 任务以本 Skill 的对应章节下发。

## 资料与展示

`.keel/bugs/<id>/investigation.md` 保存输入、证据、候选与变化。`bug.md` 是审阅和执行内容的唯一来源，固定为“问题与根因、修复方案、影响与验证”，不要求完整 Plan 文档集合、状态图或新接口设计。

独立 Python 入口复用现有 Markdown 安全渲染函数和 HTML 样式/主题脚本，生成同名 HTML 与审阅摘要；仅复用展示能力，不执行 Plan 验证或工作流。HTML 支持深浅主题、下载原始 Markdown，正文完整转义，无远程脚本或图片请求。

只有已定位、缺陷、fix 且五项设计边界均无变化，才可确认进入实施；这些声明仍需主会话及 QA 对照代码核实，不能代替证据。

## 用户确认与执行

每个 BUG 都须明确确认当前 HTML。记录用户确认原文，核对 Markdown 和 HTML 内容哈希，在独立 `runs/run-N/` 保存 approved.md 与 mode=fix 的 state.json；不存在 plan_path 或 CallChain 状态。重复确认同一版本返回原 run，保留返修次数；新版本形成新快照，旧快照保留。

调查进展写 investigation.md，执行结果写 state/QA 报告，不能追加到已确认的 bug.md 造成隐式方案变更。派发和恢复先 check，源 MD、HTML 或快照变化均阻断。确认助手只记录主会话已取得的用户决定，不替用户批准。

项目适用检查通过后，BUG_BUILD → BUG_REVIEW；阻断项进入 BUG_FIX → BUG_REVIEW_FIX，最多三轮。5/15 分钟无有效进展检查，失联先结束旧任务，每阶段每角色最多恢复两次。产物错误定向重做一次，再失败计入恢复次数。只复用公共进度助手，状态推进由主会话负责。

根因不成立暂停回到定位；新增设计变化记 NEEDS_PLAN 并提示用户转 Plan，不自动扩展链路。局部方案实质变化须停下当前执行、重渲染并重新确认，不修改旧快照。QA 通过后 WAITING_RETEST，明确收到原场景复验结果后 DONE。

## 验证

测试三栏 HTML、Markdown 下载一致性、转义/CSP、需求与设计变化拦截、证据不足不准入、审批前 MD/HTML 同步、确认后快照漂移检测、重复确认不归零，以及不依赖 Plan 的临时部署和进度记录。浏览器检查主题切换与移动布局；保留既有 ASO、Plan 和体量门禁。静态检查与运行助手测试不代替真实模型端到端评估。
