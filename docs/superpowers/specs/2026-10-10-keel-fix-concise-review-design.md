# Keel Fix 修复说明从简设计

日期：2026-10-10

用户已确认本次范围，改动归入 4.0.3。

## 目标与范围

- Fix 的 Markdown 与 HTML 只简述问题、原因、改造点、影响点和建议验证点。
- 改造点按真实类或模块列出，每项一句话说明改什么；不逐行描述代码，不展开方法调用或测试实现。
- 影响与建议验证按受影响业务流程表达，保留核对结果所必需的信息。
- Plan 与 Fix 共用独立的改造点规范；Plan 的现有文档结构保持不变。
- 调查证据、预期依据、分流结论和五项设计边界保留在既有 investigation.md，仍用于判定局部修复资格。

## 文档与运行接口

新 bug.md 固定五章：问题、原因、改造点、影响点、建议验证点。问题简述现象和预期，原因解释根因，改造点列实际类或模块，后两章从业务角度概括影响和建议回归范围。

investigation.md 的“修复资格”章节记录预期依据、证据、分流依据、定位结论、事项分类、处理路径和五项边界。只有已定位的缺陷、处理路径为 fix、五项边界均无，才允许批准执行。

沿用 validate、render、approve、check 命令及原有运行阶段。新格式在审阅和批准时绑定资格声明摘要，并保存调查快照；执行检查核对资格、修复说明、HTML 和快照。仅补充调查进展或日志不改变资格摘要，不重置已有修复次数。

HTML 展示五项简要内容，不展示调查证据、内部判定字段或代码块；保留原 Markdown 下载，不重复展示整份源文档。

## 兼容要求

旧三章 Markdown 仍按原字段判定资格，重新渲染时展示其五项核心内容。既有已批准任务不自动迁移、不重新渲染，继续使用原哈希和快照；重复批准保持原任务和次数。新模板测试之外保留固定旧格式样本。

## 实施步骤

1. 抽出共用改造点 Spec，同步 Plan/Fix 引用、模板、README 与更新日志。
2. 修改 Fix 文档解析、展示和资格摘要绑定；保持既有 CLI 与运行状态接口。
3. 覆盖精简输出、资格变化、调查补充、旧格式及部署兼容；运行相关契约与 Plan 回归检查。
4. 在临时目录生成样例并检查 HTML，完成后检查 Git 改动范围。

## 验收

- 新 MD 与 HTML 只有五项简要内容，HTML 无证据代码、分流字段及重复的完整源文档。
- 改造点规范只维护一份，Plan/Fix 均可在部署后加载。
- 不符合局部修复资格时不能批准；文档、HTML、资格或批准快照变化时阻止继续执行。
- 调查追加信息不重置已有任务；旧格式与已批准任务继续可用。
