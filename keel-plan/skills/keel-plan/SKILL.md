# Keel Plan

唯一开发依据是 `.keel/plans/<name>.md`，用户审阅入口是同名 `.html`。不生成 XML、独立 implementation 计划、业务代码或原型。

## 现状调研与决策

- 先读项目根 `AGENTS.md`，不存在时读 `README.md`。识别受影响模块的实际语言、框架、目录和验证工具链；多语言项目分别记录。模板中的 Java 示例只解释结构，必须替换为项目事实，不强制类、Service 或 Maven。
- 查找相关 `.keel/call-chain/*.md` 定位业务入口、异步推进、状态机和状态变化符号，再核对代码、模型、配置和测试。索引缺失、过期或与代码冲突时以代码为准，记录证据；不要修改 CallChain。
- 制定计划时区分已核实事实、假设和待决事项，不把推测写成现状或已确认要求。需求有多种合理解释时说明差异、影响与推荐；先核对代码和调研，仍无法确定的业务、范围或关键技术选择再询问用户。一次问一个；回答后同步推导，不得逐项询问用户确认。
- 项目已有框架和惯例时沿用；技术依据不足时查官方或一手来源，确需选型则比较 2–3 个方案并推荐。发现需求与现状冲突或存在明显更合适的方案时说明证据与权衡，不默默代选。用户已授权代选则直接决策，记录理由、影响和来源。

## 流程

1. 调研当前业务流程，区分本次开发、交互依赖和范围外内容。
2. 列出带编号、稳定英文 kebab-case slug 的本次功能目标，请用户选择生成哪些功能的时序图：部分、全部或不生成。选择只影响图表，不影响功能范围。用户已明确选择时沿用；明确授权代选时采用推荐并记录依据。不得把未回复当作不生成或代选授权。
3. 完成必要决策后，读取 `.agents/skills/keel-plan/assets/plan-template.md`，直接起草完整 Markdown。验收标准、文字目标流程、接口、代码符号改造点由 Keel 推导，不分段确认。不存在真实用户决策时不发起额外澄清轮次。
4. 每个功能保留 `### slug — 功能名`、`- 时序图：生成` 或 `- 时序图：不生成`、目标、文字目标流程和可验证验收标准。仅为选择生成的 slug 在“功能时序图”写同名三级标题和 PlantUML 围栏。全不选时写明无时序图。
5. 所有必要决策完成后写 Markdown，在项目根运行：
   `bash .agents/skills/keel-plan/scripts/render-plan-html.sh ".keel/plans/<name>.md" ".keel/plans/<name>.html"`。
6. 只报告简短范围摘要和 HTML 路径，用户集中审阅。用户反馈后修改 Markdown，同步更新所有受影响章节，再覆盖生成同一路径 HTML；禁止单独修改 HTML。
7. 用户明确确认最终 HTML 后，检查两个文件、功能覆盖、图文一致、决策和验证，再报告路径并提示 Dev。涉及状态机调整时使用 `/keel-dev`，其他需求按风险选择 full 或 fast。

## 内容要求

按模板固定章节组织：背景与范围、现有业务流程与状态机、本次功能目标、功能时序图、状态机调整、接口设计、代码改造点、技术决策与约束、实施顺序、验证方案。

- 现状写清入口、判断、异步推进、副作用、终态和证据。有业务状态机时给出现有状态图及流转表；没有时写明不适用，不虚构状态。
- 每项功能都有文字目标流程，包含正常、异常和重要副作用。验收写触发动作、输入、响应、状态或可观察副作用，不写“功能正常”。
- 接口设计关联 slug，列 API/RPC/事件的路径或签名、入参、出参、错误、权限、幂等及兼容要求；表结构、状态字段和迁移一并说明。无变化时说明依据。
- 代码改造点按 slug 列仓库相对路径、模块及实际符号（函数、类型/类、接口或方法）、当前职责和简要改造内容。既有符号核对代码，新增符号标明新增；记录契约和状态变化落点，不规定实现体或无关内部辅助函数。
- 约束只写适用项，依赖标记 `ready` / `not-ready` 并说明处理方式。实施顺序按依赖拆可独立验证的批次，验证提供工作目录、命令、业务输入和预期结果。
- “风险与恢复”按需添加：涉及数据迁移、新状态、不可逆副作用或上线切换时写触发条件、恢复动作、数据处理和恢复验证。普通修改不强制填章节，禁止只写“注意风险、支持回滚”。

## 图表约定

- 使用完整的 `plantuml` 围栏，每块只含一组 `@startuml` / `@enduml`。图放在对应章节，不生成独立图源文件。禁用外部 include、文件读取或远程资源。
- 时序图关联已选择的 slug，展示入口符号、关键服务、消息/外部系统、调用顺序、关键异常和状态变化，与接口及改造点一致。未选择的功能不画时序图。
- 状态机调整写目标状态图、本期差异图和变化说明。差异图节点用绿色 `#DCFCE7` + `[新增]`、黄色 `#FEF3C7` + `[修改]`、红色 `#FEE2E2` + `[删除]`，附图例；未变节点正常显示。删除节点只留在现状/差异图，不留在目标图。
- 边变化必须单列源/目标状态、触发事件、条件、本期变化、业务入口符号和实际改变状态的符号；只改变条件也算调整。无状态调整时说明无变化，不画无意义差异图。
- 渲染器使用本地 PlantUML（`plantuml` 命令，或 `KEEL_PLANTUML_JAR` + Java）生成嵌入图像；Python 3 必需。这些是 Keel 渲染工具依赖，不限制业务项目语言。含图而依赖缺失或图语法错误时先修复原因再重试一次，仍失败则保留 Markdown 并报告 Plan 未完成，不把源码展示当作图表成功，不提示进入 Dev。

## 完成门禁

Markdown 是 Dev、Builder、QA 的唯一计划输入；HTML 仅为派生视图。关键假设须已核实或由用户接受；不得包含 `TBD`、未决选型或把关键决策留给 Builder。检查所有功能都有验收、接口/改造映射和验证，时序图选择与实际图一致，状态图与流转表一致。HTML 成功生成且用户最终确认后才能完成。
