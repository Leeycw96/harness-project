# Keel Plan

`.keel/plans/<name>.md` 是功能索引，`<name>.features/<slug>.md` 保存各功能设计，共同作为 Dev、Builder、QA 的计划输入；同名 `.html` 用于用户评估方案。`<name>.review.md` 只保存审阅补充素材，不交给执行 Agent。不生成业务代码、原型或另一份实施计划。

## 调研与决策

- 先读项目 `AGENTS.md`，不存在时读 `README.md`，识别实际语言、架构、数据库和验证工具。模板中的 Java/PostgreSQL 仅为示例，替换为项目事实，不强制类、Service、Maven 或指定数据库。
- 参考相关 `.keel/call-chain/*.md` 定位业务入口、主要流程、异步推进和状态机，再核对代码、模型、配置及测试。索引缺失、过期或冲突时以代码为准；记录证据，不修改 CallChain。
- 区分已核实事实、假设和待决事项。优先调研可推导内容，仅询问必须由用户决定的业务、范围或关键技术选择，一次一个，不逐章确认。已有明确选择或代选授权直接沿用，不把未回复当成授权。
- 沿用项目框架与惯例；依据不足时查官方或一手来源。确需选型时比较 2–3 个方案并推荐，说明冲突与权衡，不把关键选择留给 Builder。

## 起草与审阅

1. 理解需求后拆分功能，赋予稳定英文 kebab-case slug；请用户选择哪些重点功能生成时序图，可选部分、全部或不生成。选择只影响图表，不改变功能范围，已有选择不重复询问。
2. 参考 `assets/plan-template.md` 起草轻量索引，参考 `assets/plan-template.features/` 的两个示例按功能起草 MD，并调整索引相对链接。参考 `assets/plan-review-template.md` 起草同标题审阅素材，只含背景、当前流程和按需状态机；目标、验收、模型、时序图、接口、改造点只在执行文档维护，HTML 汇总复用。
3. 在项目根运行：
   `bash .agents/skills/keel-plan/scripts/render-plan-html.sh ".keel/plans/<name>.md" ".keel/plans/<name>.html"`。
   渲染器自动读取索引关联功能文件及同目录 `<name>.review.md`。成功后报告简短摘要和 HTML 路径，请用户集中审阅。
4. 收到反馈修改对应源文件，核对受影响的索引、功能文档与审阅素材并重新生成同一路径 HTML，禁止单改 HTML。功能目标只描述技术上要达到的功能效果；接口字段与响应约定放在功能 MD 的接口设计，详细逻辑放时序图或其执行说明中，不能仅存在于审阅素材。
5. 用户确认最终 HTML 后，核对功能覆盖、图文及 SQL 一致、无未决选择，报告 HTML、索引和功能文档目录。涉及状态机调整使用 `/keel-dev`，其他按风险选择 full 或 fast。

## Markdown 执行计划

索引只保留 `## 功能目标`，每项用 `### slug — 功能名`。记录 `- 文档：[slug](<name>.features/<slug>.md)`、`- 依赖：无` 或先行功能 slug（多个用 `、`），然后写 `- 目标：…` 和 `验收标准：` 下的逐项列表。目标和验收只描述技术上要实现的功能效果，不写 HTTP 路径、字段、状态码、事务机制或实现步骤。依赖必须对应已定义功能且不能成环。

每个功能 MD 以 `# slug — 功能名` 开头，与索引一致，只包含以下四章，不重复背景、目标和验收：

- **数据模型**：用一条 `- 结构变更：新增表`、`新增字段` 或 `其他调整` 记录类型，多种用 `、` 分隔；无调整写 `- 结构变更：无`。新增表/字段必须有 PlantUML ER 图；明确字段、约束及 `sql` 围栏。仅索引、既有字段调整或回填也写 SQL，但不触发 HTML 模型章节。按项目方言及迁移约定写 SQL，必要的执行顺序和恢复要求就近说明。
- **功能时序图**：用 `- 时序图：生成` / `不生成` 记录已确认选择。选中时用 PlantUML 描述详细逻辑，图旁可简述实现约定；未选时保留必要执行说明，不强制画图。这类文字只在 MD，HTML 只汇总已选图的功能。
- **接口设计**：单独维护本功能所需的 HTTP/RPC 请求、响应和错误契约，格式同 HTML 要求；无变更写 `本功能无接口变更。`。不在时序图旁复制整份字段契约。
- **代码改造点**：直接列文件、类/方法或函数，每项仅一句话说明改什么；核实既有符号，标明新增，不重复功能分类。不得塞入 SQL、验收清单或详细步骤；Builder 根据目标、模型、时序图和接口设计完成必要联动修改。

共享模型或接口只在一个所属功能定义，其他功能在对应章节写 `- 引用：[owner-slug](owner-slug.md#数据模型)` 或 `#接口设计`，直接指向定义，不链式引用、不复制 SQL 或重复接口契约。引用功能无自身模型变更时记“无”；迁移由所属功能执行，索引声明必要的先行依赖。读取索引后仅加载当前功能及明确引用章节，依赖关系不要求加载整份依赖文档。

不另生成汇总大 MD；不新增背景、状态机、技术约束、实施顺序或验证方案章节。用户确认后，Dev 将索引及关联功能文件一起快照到 run，Builder/QA 无需读取 HTML 或审阅素材。

## HTML 审阅稿

只按以下八类内容排列，条件章节无内容时省略，不填“无变化/不适用”，不增加“其他必要说明”：

1. **背景**：仅用 `- User Story：作为…，我希望…，以便…` 列表表达理解后的用户诉求。不添加功能分类标题、slug、目标或验收标准，不要求 Story 与功能一一对应。目标和验收标准放下一独立栏目。
2. **功能目标**：独立展示技术上需要达到的功能效果及逐项验收结果，直接复用索引；不展示 HTTP 契约、事务处理等实现细节，审阅素材不重复编写。
3. **业务流程总览**：必选，在审阅素材中用 PlantUML 活动图展示当前业务入口、主要环节、关键分支和结果。参考 CallChain 并核对代码，简述证据；不展开方法调用，不把目标流程混入现状。全新业务说明当前缺少该流程，展示实际相关上下游，不虚构已有能力。
4. **状态机**：仅状态或流转条件调整时写入审阅素材，保留目标流转与本期变化；目标状态效果放 MD 功能目标，具体执行规则放时序图或执行说明。
5. **数据模型设计**：仅新增表或字段时从 MD 数据模型生成。ER 图展示本次相关表、必要关联表、主键/关联键和变化字段，标记新增/修改，说明必要类型及约束。未改的几十个字段可省略；表达关联基数，区分逻辑关系与实际外键，不虚构约束。
6. **功能时序图**：复用 MD 中已选重点功能的图，隐藏选择记录。
7. **接口设计**：仅 HTTP/RPC 有变化时从各功能 MD 汇总，按接口本身组织，不展示功能编号、slug、功能名称或目标说明。HTTP 三级标题写成 ``### POST `/path` ``，RPC 写成 ``### RPC `Service.method(Request)` ``。字段表包含类型、必填及简短说明；少量变化只写差异。请求/响应示例标明局部，删除字段不进入新示例，无请求体/响应体则直说，不虚构 JSON。
8. **代码改造点**：直接复用 MD 的文件定位和一句话说明。

## 图表与完成检查

- 图用自包含 `plantuml` 围栏，每块一组 `@startuml` / `@enduml`，不生成独立图源文件；禁用外部 include、文件读取与远程资源。ER 使用 `entity`，流程总览使用活动图。
- 时序图表达重点功能的入口、关键参与方、调用次序、重要分支、事务边界、异步交互及状态变化，与目标、模型和改造点一致。
- 状态图以新流转为主体，新增绿色 `#DCFCE7` + `[新增]`、修改蓝色 `#DBEAFE` + `[修改]`、删除红色 `#FEE2E2` + `[删除]`。删除节点放独立“本期删除”区域，不接入目标流转；变化边也标注，实际状态变化符号在 MD 中可定位。
- 检查所有功能都有目标、逐项验收、代码改造映射，已选时序图完整；ER 字段与 SQL 一致，接口与状态契约在功能 MD 中无遗漏，共享引用可达且无重复定义。关键假设须核实或获用户接受，不留未决标记或关键选型。
- HTML 需要 Python 3 和本地 PlantUML（`plantuml` 或 `KEEL_PLANTUML_JAR` + Java），图像嵌入后可离线审阅。依赖缺失或图语法错误先修复并重试一次，仍失败保留源文件并报告未完成，不把源码展示当作渲染成功，不提示进入 Dev。
