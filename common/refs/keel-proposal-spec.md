# 方案设计与编写规范（S）

## 调研结果

- 结果包含本期目标、可观察的验收结果、现状与目标的差异、影响范围、必要取舍和待决问题。
- 项目语言、架构、数据库和现有能力有实际代码或项目约定依据；模板中的 Java/PostgreSQL 仅为示例，不能作为项目事实。
- 已核实事实、假设和待决事项分别说明；资料过期或冲突有说明，现状与目标清楚区分，无需另附调查存档。
- 必要选型有官方或一手资料依据、选项和权衡；已有明确决定保持一致，最终方案没有未确认的关键业务或技术选择。

## 从简与本期范围

- 计划按本期功能目标组织，不按步骤或文件拆分功能；小调整可只有一个功能文档。
- 时序图只表达本期关键交互、业务分支和必须一起成功或失败的操作；已有逻辑合为有依据的业务块，不复述完整旧流程。
- 图中的动作使用业务短句；SQL、反复提交/回滚、错误码和等待时间等细节位于功能 MD 的必要说明或接口设计，不堆入图中。本期核心异常、异步或补偿若改变业务结果，仍在图中表达。
- 完整性按整份功能设计判断，模型、图与必要说明、接口共同覆盖本期变化；受影响的条件、事务、异常、重试和补偿都有明确依据，不要求全部进入图中，也不扩写无关旧逻辑。未选图时有精简且可执行的必要差异。
- 数据模型、接口确实无变更时，MD 保留章节并使用下文的本期不涉及标记；HTML 省略无变更的可选栏目，业务流程采用本次共用粒度规范，有流程变化时总览必需，无变化可省略。无关旧状态和调用细节不必展开，但变化的入边、出边及条件必须清楚。
- 新增状态可能改变数据库枚举/约束、SQL、接口响应枚举、校验和状态筛选，设计覆盖这些实际影响；“无新增接口/字段”不是无变更依据。文档只含变化字段，不重复完整旧接口或表结构。
- 引用本次其他功能的合约设计、模型或接口表示本期依赖该设计，保留明确引用及必要说明，不能同时标注本期不涉及。代码改造点列全必要联动，不加入无需修改的文件凑数。

正确示例：图中“事务内检查库存并保存预占”；图外说明“写事务防止并发超卖，失败全部回滚”，具体错误码位于接口设计。

## 产物约定

- `.keel/plans/<name>.md` 为功能索引，`<name>.features/<slug>.md` 为按需读取的执行设计；`<name>.review.md` 仅补充背景、本次目标业务流程和状态机。HTML 从这些源文件生成，目标、验收、合约设计、模型、时序图、接口和改造点只维护一份，不独立编造另一套审阅方案。

- 全部计划 MD（含索引、功能文档、审阅素材）及 HTML 只描述功能效果和实现设计，无开发自测内容：测试文件或测试代码改造点、测试用例与数据、测试命令、操作步骤、验证安排或执行记录。验收标准为可观察的功能结果，测试与验证在开发阶段执行。

- 审阅素材在一级标题后、背景前包含 `- 业务流程变化：有` 或 `无`，以及 `- 判定依据：…`，简述按共用粒度对比的阶段/路径，无需附代码或调查存档。这两项不作为 HTML 栏目；尚未确认的判定不能填无。

## Markdown 执行计划

- 索引只有 `## 功能目标`，每项为 `### slug — 功能名`，依次包含 `- 文档：[slug](<name>.features/<slug>.md)`、`- 依赖：无` 或先行功能 slug（多个用 `、`）、`- 目标：…` 和 `验收标准：` 下的逐项列表。目标和验收为技术上要实现的功能效果，无 HTTP 路径、字段、状态码、事务机制或实现步骤。依赖对应已定义功能且无环。

- 每个功能 MD 以 `# slug — 功能名` 开头，与索引一致，保留以下四章；涉及智能合约开发时，在数据模型之前增加 `## 合约设计`，遵守下文“合约设计标准”。不重复背景、目标和验收：

- **数据模型**：用一条 `- 结构变更：新增表`、`新增字段`、`JSON结构调整` 或 `其他调整` 记录类型，多种用 `、` 分隔；“新增表/字段”指实际数据库表/列，不包括既有 JSON 字段中的 key。无自身调整写 `- 结构变更：无`，且无本期共享模型引用时另写 `本期不涉及数据模型变更，沿用现有实现。`。内容、ER 与 SQL 的适用条件见下文“数据模型标准”。
- **功能时序图**：`- 时序图：生成` / `不生成` 与已确认选择一致。选中时 PlantUML 按上述粒度表达关键交互；图外用少量文字保留必要实现约束，不复述图表，也不另写完整实现过程。未选时有精简、可执行的必要差异。图外文字保留在 MD、下载和快照中；HTML 仅有已选图的功能标题与图，无图外实现文字。
- **接口设计**：仅包含本期变更的 HTTP、RPC 或 SDK 对调用方公开的接口契约（入参、返回值与错误/异常）。项目内部 Service、Mapper、DAO、工具类等方法不在接口设计中罗列，必要变化放执行说明或代码改造点；SDK 公开接口按实际调用边界判断，不因类名含 Service 就排除，格式同 HTML 要求；无变更为 `本期不涉及接口变更，沿用现有实现。`。时序图旁不重复整份字段契约。
- **代码改造点**：符合 `.codex/common/refs/keel-code-change-spec.md#改造点`，与目标、合约设计、模型、时序图和接口设计一致，覆盖必要联动。

- 共享合约设计、模型或接口只有一个所属功能定义，其他功能对应章节为 `- 引用：[owner-slug](owner-slug.md#合约设计)`、`#数据模型` 或 `#接口设计`，直接指向定义，无链式引用、重复定义或重复 SQL。引用功能无自身模型变更时记“无”；迁移设计归属定义功能，索引有必要的先行依赖。

- 执行计划没有额外汇总大 MD，也没有背景、状态机、技术约束、实施顺序或验证方案章节。索引及关联功能文件可独立校验和完整快照，执行所需设计不依赖 HTML 或审阅素材。

## 接口设计标准

- 仅设计本期变化的 HTTP、RPC 或 SDK 对外公开契约；内部实现方法留在执行说明或代码改造点。公开范围依据真实调用边界，不按类名判断。
- HTML 参考 `.agents/skills/keel-plan/assets/interface-example.html`：按接口签名排列，只展示入参、出参及必要局部示例，不追加失败响应、错误码清单、异常处理或“不修改订单”等结果说明。字段表含字段、类型、必填和简短说明；少量变化只列差异，不重复完整旧契约。
- 执行所需的错误/异常契约保留在功能 MD，独立成段并以 `失败响应：`、`错误：`、`异常：` 或 `错误/异常：` 开头，HTML 隐藏这些段落，下载及执行快照保留原文。不要把这些说明塞入字段说明或示例以绕过展示边界。
- 示例供参考结构与信息量，接口、字段、协议和数据替换为项目事实。源契约只维护在功能 MD，仍由统一渲染器生成正式 HTML，不直接改写另一份审阅方案。

## 时序图标准

- 使用自包含 PlantUML 时序图，HTML 展示实际渲染图像。先根据本次交互涉及的代码模块和系统边界识别用户、内部领域服务与外部方，再画交互；不要求梳理全项目领域架构，也不据此重构项目。
- 内部领域服务按订单、商品、库存等业务模块归并，一个模块通常一个参与方。Controller、Service、Mapper、DAO、模块内任务和校验器不各占一列，不按类名或技术分层展开调用链；模块内部处理用业务动作或必要自调用概括。领域服务名称表达业务职责，不虚构项目里存在独立部署的服务。
- 用户按实际角色展示；数据库、消息系统、第三方渠道和下游按本次真实交互边界保留。只有独立模块/外部系统且影响本次交互时才拆列；异步派发、回调或定时触发本身不意味着另建领域服务。参与方数量以理解关键业务交互所需为准，不设固定列数，不为减少列数合并不同业务模块或隐藏必要外部方。
- 外部参与方使用项目中可定位的业务名称，如“订单库”“导出任务库”“退款渠道”“库存系统”，不只写“数据库”“消息队列”“第三方”“下游”等泛称，也不只用 MySQL、Redis 等技术名代替业务职责。命名有实际模块、配置或调用依据；同一真实资源不因不同业务称谓拆成多个实例，不为具体命名虚构独立库或系统。
- 保留关键分支、异步边界、事务及补偿语义；归并技术参与方不等于省略业务结果或改变执行顺序。跨域调用有实际依据，同域细节和类/方法定位留在执行说明及代码改造点。参考 `.agents/skills/keel-plan/assets/plan-template.features/cancel-order.md` 的用户/订单服务/数据库/渠道归并，以及 `incremental-example.features/mark-verifying.md` 的模块内异步与校验归并；示例事实须替换为实际项目事实。

## 数据模型标准

- 只写本期结构差异、必要结构约束与数据缺省含义（如缺键表示未设置），不罗列字段用途或未改对象，不重复完整旧表、字段表、ER 与 SQL 已表达的内容。字段产生、使用、业务结果映射及校验只保留本期新增/改变且直接影响实现的必要规则，放接口设计或功能时序图/执行说明；结构或接口已表达的不重复，未改且不影响本期的不写。必要的迁移顺序和恢复要求就近保留。
- 新增实际数据库表/列时必须有 PlantUML ER 图。以 `### 订单域` 等领域标题分组，每域先放表关系图，再放对应 SQL；同域模型由一个所属功能集中定义，其他功能直接引用，不能按功能重复拆图。图中列出相关表的字段、类型和中文注释（如 `name : varchar(120) — 商品名称`），标明主键/关联键、本期变化和必要约束，关系有基数并区分逻辑关联与数据库外键。既有表只展开本次变化及理解关系所需字段，新表列全设计字段；不补造无关表或关系，单表仍可独立成图。仅索引、既有字段调整、回填或 JSON key 调整不强制 ER 图。
- 既有 JSON 字段新增、修改或删除 key 标记为 `JSON结构调整`，包含存储位置、字段路径、类型、必要结构约束和数据缺省含义；字段短表或局部 JSON 示例有一种简短且足够的表达即可，无重复描述。与数据库关系图并存时放在 `### JSON结构` 小节，避免混入领域图下的 SQL 和执行说明。
- SQL 迁移设计符合项目的数据库约束和迁移约定，可含 `- SQL迁移：需要` 或 `不需要` 标记，无未改对象清单。需要时有本次真实迁移的非空 `sql` 围栏，无注释、查询或占位语句凑数。仅应用读写新增 JSON key，未改变数据库列、约束、索引且无需历史数据迁移时，不要求 SQL；涉及这些调整则有实际迁移设计。无标记时，新增表/字段或其他调整要求 SQL，纯 JSON 结构调整不要求。

## 合约设计标准

- 涉及智能合约开发的功能有合约设计，或明确引用本期所属功能的完整设计；不涉及则无该章。适用性有需求与实际实现依据，数据库变更和时序图选择不决定适用性。
- `### 合约清单` 位于关系图前，以 `合约 | 简要说明 | 本期变化` 三列表格包含本期合约及理解关系所需的关联方；变化为“新增、修改、沿用、删除”之一。名称可定位，存在歧义时带模块限定，仅详述本期必要范围。
- `### 合约关系` 包含自包含 PlantUML 图。节点为 `class 合约名 <<contract>>`，限定名可为 `class "模块.合约名" as 别名 <<contract>>`；名称与清单一致。节点代表合约类型，两端基数描述实例关系，带部署或业务范围及必要生命周期条件。
- 关联线说明关系含义，两端标明 1:1、1:N、N:M 对应的数量，按实际约束细化为 `0..1`、`0..*`、`1..*` 等；不为凑齐三种关系补造关联。继承、调用依赖按自身语义表达，不凭调用推断实例基数，也不把合约关联当成数据库外键。单合约无关联时保留单节点图，并明确说明无关联。
- 合约设计表达职责与结构关系，执行次序和业务规则放功能时序图或执行说明，数据库表与 SQL 仍放数据模型。合约清单、图和功能实现说明须一致；共享设计直接引用定义，HTML 仅展示一份。

## HTML 审阅稿

- 只按以下九类内容排列，条件章节无内容时省略，不填“无变化/不适用”，不增加“其他必要说明”。避免解释栏目用途或复述图表的描述性文字；流程图和状态图前只用简短名称标明业务流程或状态所属对象，例如“订单取消流程”“订单状态机”“导出任务状态机”，不另写导读、图例解说、设计历史或文档分工；已有图前名称时不在图内重复标题。

1. **背景**：仅用 `- User Story：作为…，我希望…，以便…` 列表表达理解后的用户诉求。不添加功能分类标题、slug、目标或验收标准，不要求 Story 与功能一一对应。目标和验收标准放下一独立栏目。
2. **功能目标**：独立展示技术上需要达到的功能效果及逐项验收结果，直接复用索引；不展示 HTTP 契约、事务处理等实现细节，审阅素材不重复编写。
3. **业务流程总览**：按共用粒度有业务流程变化时必需；无变化可省略，用户明确要求时也可展示。一个独立业务目标通常对应一张完整生命周期活动图，不按接口或功能编号拆图；不同业务目标可分别表达。图只含触发、主要阶段、关键业务分支和结果，不展开参数格式校验、重复请求、数据库操作或方法调用等技术细节，沿用阶段合并简述。目标图明确本期新增/修改，现状符合实际实现，目标能力不冒充已有能力；全新业务也有从触发到结果的完整目标流程。现状对比位于不展示的判定依据，图前只有业务流程名称。
4. **状态机**：仅状态或流转条件调整时写入审阅素材，保留目标流转与本期变化；目标状态效果放 MD 功能目标，具体执行规则放时序图或执行说明。
5. **合约设计**：按上述适用条件从功能 MD 的定义汇总，保留先清单、后关系图的顺序；共享引用不重复展示。与数据库模型独立，不要求 SQL。
6. **数据模型设计**：新增实际数据库表/列或 JSON 结构调整时从 MD 数据模型生成，共享引用不重复展示。数据库模型按领域分别展示，每域只有领域标题、含字段/类型/中文注释的表关系图及图下对应 SQL，无图外字段表或解释段落；迁移顺序、恢复要求及缺省兼容等执行说明保留在 MD。SQL 保留换行缩进并以关键字、类型、字符串等语法着色，颜色兼容深浅主题，离线可用，不依赖 CDN。JSON 结构调整仍用存储位置加精简字段表或局部 JSON，无真实迁移时不补造 SQL。隐藏结构变更、SQL迁移与引用记录；仅索引、既有字段调整或回填的 SQL 留在执行 MD。版式参考 `.agents/skills/keel-plan/assets/data-model-example.html`，示例事实必须替换为项目事实。
7. **功能时序图**：仅展示功能标题与 MD 中已选重点功能的图，隐藏选择记录及全部图外实现文字；未选图的功能不在本栏目展示。
8. **接口设计**：仅 HTTP、RPC 或 SDK 对外公开接口有变化时从各功能 MD 汇总，按接口本身组织，不展示功能编号、slug、功能名称或目标说明。HTTP 三级标题写成 ``### POST `/path` ``，RPC 写成 ``### RPC `Service.method(Request)` ``，SDK 写成 ``### SDK `Client.method(Request)` ``。SDK 表达公开调用参数和返回值，不强套 HTTP 状态码或 JSON 请求/响应体。HTML 只展示签名、入参、出参和必要示例，错误/异常说明保留在执行 MD；按“接口设计标准”参考对应 HTML 模板。字段表包含类型、必填及简短说明；少量变化只写差异。请求/响应示例标明局部，删除字段不进入新示例，无请求体/响应体则直说，不虚构 JSON。
9. **代码改造点**：直接复用 MD 的改造点列表。

## 图表与交付标准

- 图用自包含 `plantuml` 围栏，每块一组 `@startuml` / `@enduml`，不生成独立图源文件；禁用外部 include、文件读取与远程资源。ER 使用 `entity`，流程总览使用活动图。
