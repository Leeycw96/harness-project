# 业务流程文档维护规范（S）

## 业务流程索引

- 目录 `.keel/call-chain/`，每个独立业务目标一份 `<actor>-<action>.md`；标题为“业务参与者＋要完成的目标”，如用户下单；API 调用者可泛称客户，不用“调用方调用接口”或库存占用等技术主题。
- 描述当前实现的完整主流程，不写变更日志或未实现的目标。受影响的旧文档也收敛到下述结构，不只追加内容。
- 新增文档适用于多入口推进、请求后异步推进或跨阶段状态流转；查询、单步 CRUD、DAO、DTO 等不单独建流程文档，范围不确定时简述未确认事项。

正文只有三节：

1. **主流程说明**：编号步骤，每步一句业务动作与结果；从用户/客户触发到结果，取消、失败、超时等业务分支并入对应步骤；只保留改变业务走向的分支；不展开前置条件、拒绝条件或错误清单，参数校验、重复请求和幂等返回不单独成步。
2. **状态机**：简短文本箭头，每个转移标注步骤编号或动作；只列实际改变业务状态的转移，不画重复请求或原态返回的自环；沿用真实状态，不为对应步骤编造状态，无状态机写不适用。
3. **业务入口**：类型、入口名称、业务实现符号及必要相对路径；只列推进流程的真实 HTTP/RPC 方法、MQ 消费者、业务 Job 或回调，不凑不存在的类型，不列框架配置、注册器或通用 Dispatcher。

不增加流转明细表、状态写入位置、参数、SQL/锁、日志、测试或内部调用栈。以下示例展示写法，状态、入口和路径须替换为项目实际内容。

## 完整示例

文件：`user-order.md`。

````markdown
# 用户下单业务流程

## 主流程说明

1. 用户提交订单，等待付款。
2. 支付成功后完成订单。
3. 用户取消或付款超时，关闭订单。

## 状态机

```text
未创建 --1：提交订单--> PENDING
PENDING --2：支付成功--> SUCCESS
PENDING --3：取消或超时--> CLOSED
```

“未创建”是概念起点。

## 业务入口

| 类型 | 入口 | 业务实现 |
| --- | --- | --- |
| HTTP | POST /orders | api/order.py::create |
| RPC | Order.cancel | rpc/order.py::cancel |
| MQ | payment.succeeded | consumers/payment.py::handle |
| 定时任务 | 超时关单 | jobs/order_timeout.py::execute |
````
