# 代码与测试质量（S）

## 代码与测试标准

- 被验收的实现和补充测试应满足同一标准。代码、注释、框架、目录和测试写法沿用项目约定，不强制引入类、Service 分层或新测试框架。

- 接口、数据保存和命令行等已确认功能真实可用，不以 stub、fake、固定成功结果或 TODO 代替；假实现属于阻断项。依赖缺失或其他阻塞有缺项与影响说明；测试替身仅隔离外部系统，真实业务逻辑和关键联动须实际验证。

- 缺陷修复应解决已确认根因，符合原有要求；本次产生的无用代码应已清理。

- 测试覆盖别人会调用的业务能力，对象可为函数、模块或类方法，包含关键正常、异常和状态、数据、消息变化，缺关键测试属于阻断项。纯文案或机械修改不要求额外测试；内部转发、数据容器或简单转换可随业务能力覆盖，有独立规则、边界风险或项目要求时有对应测试。接口路由、权限、数据格式、消息和持久化联动按风险进行验证，范围不以文件类型或 public 关键字划分，不要求新增分层。

- 实现符合项目职责划分：接口、消息、定时任务等入口处理输入格式、权限、校验并调用业务能力，业务规则位于可验证的业务模块或函数；职责越界属于阻断项。校验、鉴权和协议错误处理可有条件分支，if/for 数量不是违规标准，不要求 Controller/Service 分层。

- 测试须有核对业务返回结果、状态、数据或消息变化的断言；空测试、只打印日志或只检查“不抛异常”不能算业务验证通过。测试文件的名字、后缀、目录和运行方式沿用项目约定，补充测试同样适用，不强制同包或 `.java` 后缀。

- 每次提交保持项目适用的构建、类型/语法、测试和启动检查可用。项目没有编译步骤时有适用检查即可。简述实际运行结果，无需保存命令、工作目录、输出或日志；不适用有理由，未运行不能记通过，失败标明本次新失败、已有失败或环境限制。
