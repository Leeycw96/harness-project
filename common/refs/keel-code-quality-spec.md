# 代码与测试质量（S）

## 代码与测试标准

- 被验收的实现和补充测试应满足同一标准。代码、注释、框架、目录和测试写法沿用项目约定，不强制引入类、Service 分层或新测试框架。

- 接口、数据保存和命令行等已确认功能应真实可用，不能以 stub、fake、固定成功结果或 TODO 代替；假实现须阻断验收。依赖缺失或其他阻塞须记录缺项与影响；测试替身仅用于隔离外部系统，真实业务逻辑和关键联动仍须验证。

- 缺陷修复应解决已确认根因，符合原有要求；本次产生的无用代码应已清理。

- 测试范围是别人会调用的业务能力，测试对象可按项目结构使用函数、模块或类方法，覆盖关键正常、异常和状态、数据、消息变化，缺关键测试须阻断。纯文案或机械修改不要求额外测试；内部转发、数据容器或简单转换可随业务能力验证，有独立规则、边界风险或项目要求时须覆盖。接口路由、权限、数据格式、消息和持久化联动按风险验证，不按文件类型一概排除，不以 public 关键字决定范围，不强制新增分层。

- 实现应符合项目职责划分：接口、消息、定时任务等入口处理输入格式、权限、校验并调用业务能力，业务规则位于可验证的业务模块或函数；职责越界须阻断验收。校验、鉴权和协议错误处理允许条件分支，不以 if/for 数量判断违规，不强制 Controller/Service 分层。

- 测试须有核对业务返回结果、状态、数据或消息变化的断言；空测试、只打印日志或只检查“不抛异常”不能作为业务结果证据。测试文件的名字、后缀、目录和运行方式沿用项目约定，补充测试同样适用，不强制同包或 `.java` 后缀。

- 每次提交应保持项目适用的构建、类型/语法、测试和启动检查可用。项目没有编译步骤时提供适用检查即可。项目声明的适用检查须有命令、工作目录、结果和证据；不适用须有理由，未运行不能记通过，失败须标明本次新失败、已有失败或环境限制。
