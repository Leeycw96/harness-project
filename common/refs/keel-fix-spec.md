# Keel Fix Spec（S）

## 适用范围

局部修复针对已确认要求下、根因明确且不改变既定设计的实现缺陷。缺陷标签或改动行数不能代替影响判断；证据不足时保持待判断。

预期行为改变、新增需求，或涉及业务状态/流转、业务流程、接口契约、数据模型/迁移，以及需要专项设计的权限、事务并发或跨模块调整，均需方案设计。内部条件或计算修正不必然改变业务流程；流程索引需要记录的状态、流转或执行符号变化仍属于设计影响。

## 修复说明

修复说明是独立的 Markdown 文档，以 BUG 标识与简短名称为一级标题，仅包含以下三章，示例内容替换为项目事实：

1. **问题与根因**：当前现象、预期行为、预期依据、定位结论、根因、证据、事项分类、处理路径、分流依据。
2. **修复方案**：修复目标、代码改造点，以及业务状态调整、业务流程调整、接口契约调整、数据模型或迁移、高风险设计五项边界。改造点逐项定位文件/符号并用一句话描述改动。
3. **影响与验证**：影响范围、逐项回归验证、现场待验证事项；区分可验证的代码行为与原场景复验。

定位结论为“已定位、候选原因、暂未定位”之一；事项分类为“缺陷、需求变更、待判断”之一；处理路径为“fix、plan、待补证据”之一。五项边界据实填写“无、有、待确认”，只有“已定位、缺陷、fix”且五项均“无”的说明符合局部修复要求。边界声明须有证据，不能借修复说明改变业务约定。

## 验收依据

实现与验收依据已确认修复说明及本次开发质量标准，核对根因证据、目标和实际变更范围。验证报告须说明已验证行为、关联回归与现场缺口；代码检查通过不代表原场景已经复验。实际影响超出局部修复范围时不满足验收要求，须列出证据及所需设计。
