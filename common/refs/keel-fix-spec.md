# Keel Fix Spec（S）

## 适用范围

局部修复针对已确认要求下、根因明确且不改变既定设计的实现缺陷。缺陷标签或改动行数不能代替影响判断；证据不足时保持待判断。

预期行为改变、新增需求，或涉及业务状态/流转、业务流程、接口契约、数据模型/迁移，以及需要专项设计的权限、事务并发或跨模块调整，均需方案设计。内部条件或计算修正不必然改变业务流程；流程索引需要记录的状态、流转或执行符号变化仍属于设计影响。

## 修复说明

修复说明以 BUG 标识与简短名称为一级标题，仅包含以下五章。各章用简短、易懂的说明，示例事实替换为项目事实：

1. **问题**：简述现象和预期结果。
2. **原因**：用短句解释根因。
3. **改造点**：遵守 `.codex/common/refs/keel-code-change-spec.md#改造点`。
4. **影响点**：概括受影响的业务流程或能力。
5. **建议验证点**：建议回归哪些业务流程及关键结果，必要时指出原场景仍待复验。

除改造点列表外使用短段落，不展开证据代码、行号、内部判定字段、测试用例、测试文件或执行步骤。HTML 直接展示这五项内容，不重复展示完整源文档；Markdown 可下载。

## 修复资格

预期依据、证据和分流结论保留在同目录 `investigation.md`，不写入新修复说明。其 `## 修复资格` 章节用固定字段记录：

- 预期依据：已确认要求及出处。
- 证据：支持根因和边界判断的实际代码、日志或复现资料。
- 分流依据：为什么适合局部修复或需要设计。
- 定位结论：已定位、候选原因、暂未定位之一。
- 事项分类：缺陷、需求变更、待判断之一。
- 处理路径：fix、plan、待补证据之一。
- 业务状态调整：无、有、待确认之一。
- 业务流程调整：无、有、待确认之一。
- 接口契约调整：无、有、待确认之一。
- 数据模型或迁移：无、有、待确认之一。
- 高风险设计：无、有、待确认之一。

仅“已定位、缺陷、fix”且五项边界均“无”符合局部修复要求。声明须有证据，不能借修复说明改变业务约定；调查进展可在其他章节补充。

旧三章说明（问题与根因、修复方案、影响与验证）仍可读取，其资格字段沿用原位置；新任务使用五章格式。旧格式重新渲染时只展示五项简要内容，既有已批准任务沿用原快照。

## 验收依据

实现与验收依据已确认修复说明、对应调查依据及本次开发质量标准，核对根因证据、目标和实际变更范围。新格式以 `approved.md` 和 `approved-investigation.md` 为依据，旧任务沿用已有资料。验证报告须说明已验证行为、关联回归与现场缺口；代码检查通过不代表原场景已经复验。实际影响超出局部修复范围时不满足验收要求，须列出证据及所需设计。
