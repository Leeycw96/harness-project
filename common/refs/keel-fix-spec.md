# Keel Fix Spec（S）

## 适用范围

### 局部缺陷

简要描述：根因明确、已有确认要求且不改既定设计的实现缺陷可修复；按实际影响判断，不能看缺陷标签或行数，缺证据时保持待判断。

### 设计边界

简要描述：改变预期、新增需求，或调整业务状态/流转、业务流程、接口契约、数据模型/迁移，以及需专项设计的权限、事务并发或跨模块改动，均需方案设计。内部条件或计算修正不一定改变流程；流程索引需记录的状态、流转或执行符号变化仍属设计影响。

正确示例：复用已有舍入规则修正折扣金额，可按局部缺陷处理。

## 修复说明

### 说明结构

简要描述：一级标题为 BUG 标识与短名称，仅写以下五章；内容简短易懂，示例替换为项目事实。

1. **问题**：现象与预期结果。
2. **原因**：用短句解释根因。
3. **改造点**：遵守 `.codex/common/refs/keel-code-change-spec.md#改造点`。
4. **影响点**：受影响的业务流程或能力。
5. **建议验证点**：建议回归的业务流程与关键结果，必要时标明原场景待复验。

### 展示从简

简要描述：改造点用列表，其余用短段落，不展开证据代码、行号、内部判定、测试用例/文件或步骤。HTML 只展示这五项，不重复完整源文档；保留 Markdown 下载。

## 修复资格

### 资料分工

简要描述：预期依据、证据、分流结论保留在同目录 `investigation.md` 的 `## 修复资格`，不写入新说明；固定字段如下：

- 预期依据：已确认要求及出处。
- 证据：支持根因和边界判断的实际代码、日志或复现资料。
- 分流依据：为什么适合局部修复或需要设计。
- 定位结论：已定位、候选原因、暂未定位之一。
- 事项分类：缺陷、需求变更、待判断之一。
- 处理路径：fix、plan、待补证据之一。
- 业务状态调整：无、有、待确认之一。
- 业务流程调整：无、有、待确认之一。
- 接口契约调整：无、有、待确认之一。
- 数据模型或迁移：无、有、待确认之一。
- 高风险设计：无、有、待确认之一。

### 资格完整

简要描述：仅“已定位、缺陷、fix”且五项边界均“无”可局部修复；声明须有证据，不借说明改变业务约定。调查进展可写在其他章节。

### 旧任务兼容

简要描述：新任务用五章；旧三章（问题与根因、修复方案、影响与验证）及原位置资格字段可读，重渲染只展示五项简述；已批准任务沿用原快照。

## 验收依据

### 确认依据

简要描述：按已确认说明、调查依据与本次开发质量标准核对根因证据、目标和实际改动；新格式使用 `approved.md`、`approved-investigation.md`，旧任务沿用已有资料。

### 验证结论

简要描述：报告已验证行为、关联回归与现场缺口，代码检查通过不等于原场景已复验；影响超出局部修复范围时不能验收，须列证据与所需设计。
