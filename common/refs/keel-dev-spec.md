# Keel Dev Spec（S）

## 操作约束

简要描述：按项目手册和本次专项规范工作。规范冲突或缺少必要资料时说明问题，不自行降低要求。

- **工作范围**：在用户授权内修改业务代码、测试并提交本次改动；不修改业务流程索引，不编造验收报告。
- **保留已有工作**：只暂存本次授权文件，保留用户无关改动；不自行合并、压缩、推送或清理已有提交。
- **资料范围**：只读取本次任务相关资料，不翻阅无关历史运行记录。规范允许的操作也须在本次授权内。

## 问题定位

### 只读调查

简要描述：可查看相关代码、配置、已有测试和已提供的日志，运行授权检查。定位时不修改业务代码、测试、配置或数据，不加日志代码、不提交；需要改代码取证时先说明需求。

### 用证据判断原因

简要描述：按已确认的要求判断对错，记录代码版本、日志来源和现场条件。本地复现有帮助，但不是必要条件；发现代码缺陷时仍要说明它为什么能解释本次现象。

错误示例：代码里有日志语句，就断定本次运行经过该分支；没有日志，就断定事件未发生。

### 分清确定程度

简要描述：结论使用“已定位、候选原因、暂未定位”。已定位要有能解释现象的证据；不确定时列出查过什么、支持和反对证据，以及还不能确定什么，不猜测补全。

### 有目的地补资料

简要描述：多个候选原因分别给出区分方法。请求日志时说清关键字或代码位置、时间范围或请求标识、必要字段和用途。只索取必要信息；拿不到证据就如实说明，不能写成已排除。

### 分清代码验证与现场复验

简要描述：无法复现原场景时，说明哪些代码行为可以验证、哪些仍需现场核对。回归测试通过、诊断日志补齐、原 BUG 已消失分别记录，不能互相代替。

## 代码与测试标准

简要描述：实现和验收使用同一标准。代码、注释、框架、目录和测试写法沿用项目约定，不强制引入类、Service 分层或新测试框架。假实现、职责越界或缺少关键测试须阻断验收；个人风格偏好不阻断。

### 1. 真实实现

简要描述：没有依赖缺失或其他阻塞时，代码必须真正完成需求，接口、数据保存和命令行功能要真实可用。有阻塞时说明缺什么、影响什么，不伪造数据或悄悄跳过功能。

错误示例：业务代码用 stub、fake 或固定成功结果代替实现，或只写 TODO 就报告完成。

正确示例：测试中用替身隔离外部系统，同时验证真实业务逻辑和关键联动。

### 2. 修复根因

简要描述：修复要解决问题根因。测试失败先检查实现和约定，不改断言或参数掩盖错误。只做本次授权所需的修改，不顺手重构、改格式或添加未要求的抽象；清理本次造成的无用代码，原有无关问题只报告。

### 3. 测试范围与边界

简要描述：验证别人会调用的业务能力，覆盖关键正常、异常情况和状态、数据或消息变化。按项目结构选择函数、模块或类方法，不为测试另造一层；是否对外可用不取决于 public 关键字。

纯文案或机械修改不硬凑测试。没有独立规则的内部转发、数据容器或简单转换，通常随业务能力一起验证；有独立规则、边界风险或项目要求时补测，不按文件类型一概排除。接口路由、权限、数据格式、消息和持久化联动按风险用项目已有方式验证。

### 4. 入口与业务边界

简要描述：沿用项目职责划分。接口、消息、定时任务等入口处理输入格式、权限、校验并调用业务能力；业务规则放在可验证的业务模块或函数中。校验、鉴权和协议错误处理可以有条件分支，不凭 if/for 数量判断违规，不强制 Controller/Service 分层。

### 5. 测试质量

简要描述：用断言核对返回结果、状态和数据或消息变化。测试文件的名字、后缀、目录和运行方式沿用项目约定，QA 补充的测试也一样，不强制同包或 `.java` 后缀。

错误示例：空测试、只打印日志，或只检查“不抛异常”，没有核对业务结果。

### 6. 持续可验证

简要描述：每次提交保持项目适用的构建、类型/语法、测试和启动检查可用。项目没有编译步骤时运行适用检查即可。运行项目声明的适用检查，记录命令、工作目录、结果和证据；不适用要说明理由，未运行不能写通过。区分本次新失败、已有失败和环境限制。
