# Keel Dev Spec（S）

## 操作约束

项目手册及本次提供的专项规范补充语言、架构、目录和验证命令。发现规范冲突或必要资料缺失时报告，不自行放宽约束。

- 实现工作：可修改任务范围内的业务代码和测试，允许提交本次改动；不能修改业务流程索引或编造验收报告。
- 保留用户无关改动；只 stage 本次授权文件，不自动 merge、squash、push 或清理已有提交。
- 不读取与任务无关的历史运行资料。规范允许的操作仍受本次任务范围和用户授权限制。

## 代码与测试标准

所有写代码和验收动作遵守以下规则。语言、框架、模块边界、命名与目录沿用项目约定；不强制引入类、Service 层或特定测试框架。具体语言示例只解释原则，不构成项目要求。

### 1. 真实实现

- API、数据持久化和 CLI 必须真实可用，不用 stub、fake 或硬编码成功响应代替交付。此类假实现、违反项目职责边界及缺少关键测试均为验收阻断；纯风格偏好不阻断。
- 依赖未就绪时明确记录阻断及影响，不伪造数据或静默跳过已承诺功能。注释采用项目语言的语法。
- 测试中的替身可以隔离外部系统，但不能替代对真实业务实现和关键集成的验证。

### 2. 修复根因

- 测试失败先检查实现和契约，不修改断言或参数来掩盖错误。
- 交付应解决问题根因并保持授权范围；不得用未要求的抽象、无关重构或格式改动扩大交付。清理本次造成的无用代码，原有无关问题只报告。

### 3. 测试范围与边界

只增加有助于验证行为的测试，不为简单文案或机械修改强造测试。

- 测试须覆盖对外业务契约的关键正常、异常分支和副作用；“对外”指业务模块供调用方使用的行为，不取决于 public 关键字或是否为类方法。
- 测试对象可以是函数、模块、类型方法或用例处理器，按项目架构定位，不为满足 Keel 命名规则新增抽象层。
- 无独立行为的内部转发、纯数据容器和机械转换不强制重复单测；内部实现通常经业务契约覆盖。存在独立规则、边界风险或项目明确要求时补充针对性测试，不按文件类型一律禁止测试。
- 路由、权限、序列化、消息协议和持久化集成按风险通过项目已有测试方式验证。
- 示例（仅作映射）：Java 的 `OrderService.cancel`、Go 的 `order.Cancel`、Python 的 `orders.cancel_order` 均可承载同一个取消订单契约。

### 4. 入口与业务边界

- 遵循项目既有职责划分。HTTP/RPC 处理器、消息消费者、定时任务等入口负责协议适配、校验和调用业务能力；业务规则集中在可验证的业务模块或函数中。
- 不把项目强行改造成 Controller/Service 分层。校验、鉴权和协议错误处理所需的条件分支允许留在入口；是否违反边界取决于职责，不按 if/for 等语法判断。

### 5. 测试质量

- 断言明确验证响应、状态或副作用；空测试、只打印日志或只验证“不抛异常”不构成验收。
- 测试命名、扩展名、位置和发现规则沿用项目约定，包括 QA 补充的测试，不强制同包或 `.java` 后缀。
- 示例：Java 项目可能使用 `OrderServiceTest.java`，Go 使用 `order_test.go`，Python 使用 `tests/test_orders.py`；以实际测试配置为准。

### 6. 持续可验证

- 每个 commit 保持项目适用的构建、类型/语法检查、测试和启动验证可用；不要求所有语言都有独立编译阶段。
- 运行项目声明的检查并记录命令、工作目录、结果和证据；不适用的检查写明理由，不能把未执行记录为通过。
- 不把本轮新增失败算作既有问题，也不把已明确记录的环境或基线问题直接判为本轮回归。
